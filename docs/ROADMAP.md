## 3a. AI/ML: где это в коде

Три разные сущности, которые в ТЗ/хакатоне называют «AI»:

- **ML-модель аномалий (функция №9, §15).** Реальный `IsolationForest`
  (scikit-learn) с запасным детектором на чистом numpy (`robust_profile`:
  медиана и MAD по признакам), чтобы вкладка работала в любой установке;
  активный алгоритм виден в `/api/anomalies/status` и в записи модели:
  `backend/app/analyzers/anomaly_detection.py`. Признаки
  сообщения (длина, энтропия, уникальные байты, доля нулей, printable, повторы,
  направление, межсообщенческий интервал, число диагностик) и сессии — точно по
  §15. Эндпоинты `/api/anomalies/{status,train,score,models}`, UI
  `frontend/app/anomalies/page.tsx`. Требует ≥50 сэмплов baseline, предупреждает
  при <500, фиксирует seed/параметры/версию sklearn. Это **настоящая модель**.
- **LLM (функция №10, §16).** Локальный **Ollama** через `/api/chat`,
  провайдер-интерфейс (`OllamaProvider`/`NullProvider`):
  `backend/app/reporting/llm.py`, `reporting/assistant.py`, роутеры
  `app/api/routers/assistant.py` и `reports.py` (`use_llm`). Модель только
  «пересказывает» уже проверенные факты; системный промпт запрещает выдумывать
  события; контекст редактируется (`redact`) и ограничивается по размеру.
  Это **настоящий LLM-путь**, но опциональный.
- **Алгоритмический реверс-инжиниринг (функция №8, §11/§14).** Не нейросеть, а
  детерминированные статистики: `framing.py` (в т.ч. метод `heuristic` —
  синхронизация + энтропия + консистентность длин), `byte_analysis.py`,
  `field_inference.py` (гипотетические поля с ролями
  magic/version/message_type/length/identifier/parameter/status/checksum/…,
  уверенность и supporting/contradicting-примеры), `protocol_detection.py`.
  Это соответствует ТЗ (для №8 модель не требуется), но в тексте хакатона
  называется «AI».

Почему AI выглядит «отсутствующим»:

- внешний AI **выключен по умолчанию** (`MPLAB_ALLOW_EXTERNAL_AI=false`) и
  включается только через `.env`; в UI согласия нет;
- кнопка «Generate report» на странице Reports **не передаёт `use_llm`**, поэтому
  LLM-путь доступен только из Assistant;
- Ollama в окружении **не установлен**, поэтому LLM-нарратив сейчас не
  запускается из коробки (приложение корректно деградирует);
- нет автотестов на AI/ML-пути (деградация без LLM, редактирование секретов,
  воспроизводимость модели).

   (ключевой блок через PRF RFC 5246) и TLS 1.3 AES-GCM/ChaCha20-Poly1305
   (`HKDF-Expand-Label`, nonce = IV XOR seq). Набор шифров берётся из ServerHello,
   при необходимости — из соседнего направления той же сессии.
4. UI: страница `app/tls` — загрузка/просмотр/удаление журналов, выбор потока и
   журнала, таблица записей со статусом и открытым текстом.
5. Безопасность: ключевой журнал не попадает ни в отчёт, ни в AI-контекст, ни в
   архив `.mplab` (он не входит в состав экспорта проекта).
6. Тесты: round-trip'ы на **реально построенном шифротексте** (18 тестов:
   TLS 1.2 GCM/CBC, TLS 1.3 GCM, отказ по неверному ключу, флип байта,
   обрезанная запись, неподдерживаемый набор) + 7 API-тестов (загрузка/выдача/
   удаление, отказ чужого журнала).
**Приёмка:** запись возвращается с открытым текстом только при успешной
аутентификации; всё остальное сообщает причину. Проверено вживую на
`data/testbench/tls_handshake.pcap`: набор шифров определён, при отсутствии
нужного секрета в журнале — честный отказ, 0 байт открытого текста.
**Ограничения:** наборы шифров вне списка и неполные ключевые журналы
невозможно расшифровать — это сообщается, а не аппроксимируется.

### 8.8. Реверс-инжиниринг неизвестного бинарного протокола — ✅ (Этап 2)
**Есть:** границы сообщений (`heuristic`, `length_prefix`, `delimiter`,
`signature`), статистика байт (энтропия, колонки, корреляции), гипотетические
поля с ролями и уверенностью, evidence-supporting/contradicting. Подтверждено на
реальном протоколе «Термостенд».
**Сделано (Этап 2):** backend — классификация байтовых колонок в
`column_statistics`/`classify_column` (`byte_analysis.py`): `constant`, `counter`
(монотонность ≥80%), `enum` (≤16 значений), `high_entropy` (энтропия ≥6.5 бит и
частая смена), `variable`, `absent`; у каждой колонки — `monotonic_ratio` и
`classification_rationale`. **Честность:** `checksum` намеренно не выделяется в
отдельный класс — статистика не отличает контрольную сумму от случайных/сжатых/
шифрованных байтов, поэтому `high_entropy` прямо это оговаривает. Frontend
(workbench): цветовая полоса классов по офсетам, легенда и колонка «Class» с
подсказкой-обоснованием (`lib/column-classes.ts`). Сквозная проверка на
`sample_protocol`: `tests/test_sample_protocol.py` импортирует реальный
`research/01_configuration.pcap`, **сам выводит** правило кадрирования
(`length_offset=2`, `size=2`, BE, `includes_header=false`, `header_size=8`),
magic `0xA65C`, `sequence` @4 (req_id), `message_type` @7 (команда) и классы
колонок (`constant`/`counter`/`enum`); сообщения проверяются как `total =
declared + 8`. Все кандидаты маркированы как гипотезы.
**План:** осталось (опционально) LLM-именование полей.
**План:**
1. Backend: экспонировать классификацию байтовых колонок — `constant/header`,
   `counter/id` (монотонность/частота изменений), `random/crypto` (высокая
   энтропия), `checksum`; добавить в статистику полей.
2. Frontend (workbench): раскрасить колонки по классу, рядом — гипотетические поля.
3. Сквозная проверка на `sample_protocol` (Этап 2).
